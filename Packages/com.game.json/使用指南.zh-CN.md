# Game Config 0.4.0 使用与交付说明

## 1. 最终交付是什么

这是一个可以独立安装的 Unity UPM Package，不依赖小游戏、Lua 框架或资源管理框架。
包标识保留为 `com.game.json`，命名空间保留为 `GameJson`，但构建核心不再依赖 JSON。

三个目标始终不变：紧凑的配置常驻内存、高效的类型化读取、约定热路径预热后的零托管分配。
零 GC 在本文中指零新增托管分配，不是控制全局垃圾回收器，也不包含加载和编译。

## 2. 五分钟跑起来

1. Unity 2022.3 中打开 `Window > Package Manager`。
2. 选择 `+ > Add package from tarball`，安装 `com.game.json-0.4.0.tgz`。
3. 在包的 Samples 中导入 `Source Independent`。
4. 执行 `Tools > Game-Json > Verify source-independent sample`。
5. Console 应出现 `SOURCE SAMPLE PASSED: JSON == CSV == C#`。
6. 新建一个 GameObject，挂上 `SourceSampleReader`，把样例的 `SourceConfig.bytes` 拖入 `PackedConfig`。
7. 点击 Play，Console 输出 Tile 5 的奖励为 20 金币、名称 Welcome。

样例自带生成代码和二进制，不要求先安装 .NET SDK 或搭建整个游戏。
示例中的 Console 输出会分配内存，不能拿日志调用验证零 GC。

## 3. 数据如何流动

```text
JSON 导入器 ─┐
CSV 导入器 ──┼─> ConfigDocument ─> 公共校验 ─> 二进制 + 生成 C#
自定义来源 ──┘                                      │
                                                  v
                                  CompactConfig + 类型化只读访问
                                                  │
                                                  v
                                     一次 Capture 的业务操作
```

源格式只影响导入步骤。运行时不需要知道配置来自 JSON、CSV、表格导出工具还是服务端生成器。
“通用”意味着统一配置语义和扩展入口，不意味着任意文件无需适配就能读取。

| 层 | 对应程序集 | 负责什么 |
| --- | --- | --- |
| 运行时 | `Game.Json.Compact` | 校验并加载二进制、列存储、索引、只读视图、快照发布 |
| 构建核心 | `Game.Config.Build` | 类型化模型、默认值、主键和引用校验、编译、代码生成 |
| JSON 适配器 | `Game.Config.Json` | JSON 转模型，以及旧接口兼容 |
| CSV 适配器 | `Game.Config.Csv` | 有明确 Schema 的 CSV 转模型 |
| Unity 工具 | `Game.Json.Compact.Editor` | 文件输出和菜单，不进入 Player |

运行时和构建核心没有 Newtonsoft 引用。完整包仍声明 Newtonsoft 依赖，供 JSON 适配器和工具使用。
构建程序集并非被强制标为 Editor-only，以便离线 .NET 工具和需要运行时编译的既有项目复用。
业务 Player 通常只需运行时和生成访问代码，不应在每帧调用导入器。

## 4. 接入新的数据源

实现 `IConfigSource.Read()`，返回 `ConfigDocument`。返回值包含版本、表结构、行和明确类型的值。
不要把原始 JSON 节点或 `Dictionary<string, object>` 塞进运行时。

```csharp
public sealed class MySource : GameJson.IConfigSource
{
    public GameJson.ConfigDocument Read()
    {
        var table = new GameJson.ConfigTableSchema("Reward", new[] {
            new GameJson.ConfigField("id", GameJson.FieldKind.Int),
            new GameJson.ConfigField("coins", GameJson.FieldKind.Int)
        });
        return new GameJson.ConfigDocument(1, new[] {
            new GameJson.ConfigTableData(table, new[] {
                new GameJson.ConfigRow(new[] {
                    GameJson.ConfigValue.Int(1), GameJson.ConfigValue.Int(20)
                }, "my-source:row-1")
            })
        });
    }
}
```

构建调用：

```csharp
var document = new MySource().Read();
byte[] bytes = GameJson.ConfigBuild.Compile(document);
string code = GameJson.ConfigBuild.Generate(document, "MyGame.Config", "GameConfig");
```

Unity 工具层可以使用 `GameJson.Editor.ConfigMenus.GenerateSource(source, directory, namespaceName, className)`。
源码仓库附带命令行工具，CI 可调用：

```powershell
dotnet run --project Tools/GameJson.Tool -c Release -- source.json output MyGame.Config GameConfig
dotnet run --project Tools/GameJson.Tool -c Release -- --csv schema.json csv-folder 1 output MyGame.Config GameConfig
```

第二条命令用 JSON 方便地声明 Schema，但 CSV 适配器本身不要求 JSON。
包内示例直接用 C# 声明 Schema，独立无 JSON 消费者也验证了这条路径。
每张表对应一个同名 CSV 文件；工具要求表名能安全用作文件名。
命令失败返回非零退出码。每个输出文件单独替换，不承诺两个文件的跨文件崩溃原子性；CI 应把完整成功产物作为一组发布。

## 5. 配置约定

- 支持 `int`、`long`、有限值 `float`、`bool`、`string`、`int[]`。
- 第一列必须是 `id:int`，非负、唯一、不可配置默认值。
- `int` 和 `int[]` 可声明引用目标表；不存在的表或目标 ID 会导致构建失败。
- 版本是正整数内容修订号，不是二进制格式号。
- 默认值必须显式声明且类型匹配。未提供的字段才使用默认值；显式 null 会报错。
- CSV 表头允许重排；未知字段、重名表头、缺少必填列会报错。
- CSV 支持双引号包裹、引号转义、字段内换行；列表用分号分隔，布尔用 true/false。
- 空字符串和空列表合法；空数值不自动视为零。空白行不静默忽略，字符串不统一 Trim。
- 原生 XLSX、可空类型、任意嵌套对象、复合主键不是本版本能力。

模型构造会复制调用方的集合，避免编译期间被外部修改。模型本身允许分配，不能用于证明运行时内存紧凑。
公共校验负责不同来源的同一套语义，诊断尽可能带上来源、表、行和字段。

## 6. 三个目标如何兑现

**紧凑内存：** 运行时不是每行一个对象。数值按类型放在列数组里，布尔位压缩，列表使用连续值池，重复字符串在列内共享。
连续主键使用算术定位，适度稠密主键使用行偏移索引，稀疏主键按策略选哈希或二分。
这是托管列数组方案，不是零拷贝、内存映射或全体数据都连续的一块内存。

**高效访问：** 生成代码提前绑定列句柄，读取不反复查字段名和转换类型。
跨表引用绑定到所属快照。批量数值扫描可以取只读 Span，避免逐行包装开销。
并不保证每种查找都胜过 DTO 字典，稀疏查找和逐行扫描的负面结果也保留在验证报告中。

**零分配热路径：** 行视图、列表视图、枚举器为值类型，字符串复用加载时对象。
预热后测试类型字段、查找、引用导航、遍历、快照 Capture 的分配。
加载、代码生成、绑定、更新发布、异常、日志、LINQ 和接口装箱不在零分配承诺内。

## 7. 更新与生命周期

更新分为 Prepare 和 Commit，候选数据先加载、校验和绑定，成功提交才改变当前快照。
同一个业务结算应 Capture 一次，所有跨表读取都使用该快照，避免一个回合读到两个版本。
读路径不加锁；提交串行化，拒绝过期、重复和属于其他 Store 的票据。
严格递增修订号需要显式选择 `ConfigVersionPolicy.Increasing`。

旧行仍然有效，也会保留其所属快照。释放业务引用后由 GC 回收；不要永久缓存旧行。
多版本并存和加载期间需要额外内存，常驻内存指标不等于更新峰值。
取消候选时 Dispose 票据；这不会销毁已经发布的快照。
文件校验和用于检错，不代表签名认证；此包不负责下载、签名、CDN 或落盘事务。

## 8. 老项目升级

原 `ConfigCompiler.Compile(string)`、`ConfigCodeGenerator.Generate(string, ...)` 和动态读取 API 保留。
原 GJC2 格式保持不变，旧三类型 GJC1 可继续由动态 API 加载。
自定义 asmdef 如调用编译器、生成器或 `ObjectConfig`，需要新增 `Game.Config.Json` 引用。
使用新模型和构建 API 时引用 `Game.Config.Build`；运行时读取仍只引用 `Game.Json.Compact`。
迁移后程序集位置改变，预编译 DLL 或程序集限定类型名的消费者必须重新编译或调整。

## 9. 如何验收

精确平台、测试数量和实测数据见 `VERIFICATION.md`。包外源码仓库保留脚本、原始数据和版本化证据。
不要把 .NET 数据当成手机数据，也不要把“未检测到 GC”当成“检测器校准后确认为零”。
任何评分都应建立在可复现代码、取舍和测试证据上，本包不承诺面试分数。
