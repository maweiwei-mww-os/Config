# Game-Json 0.3.1 框架验收与面试说明

本轮的交付对象是配置框架，不是小游戏展示页。独立包位于
`Packages/com.game.json`，发布包为 `Distributions/com.game.json-0.3.1.tgz`。
小游戏只是保留的兼容性消费者；框架测试与 Unity 验证工程均不依赖游戏代码。

## 1. 实际解决的问题

传统 JSON 配置在运行时展开成大量对象、数组、重复字符串和字典，容易造成
启动解析成本、常驻内存和对象数量上升。优化配置存储之后，还必须保证业务
易用性、版本兼容、更新一致性和生命周期正确，不能只做一个读取数字很快的容器。

这一版保留 JSON 作为策划输入，将解析和校验尽量前移到构建期，在客户端使用
紧凑列存储、生成的强类型接口，以及显式的配置快照发布。

## 2. 完整链路

```text
JSON 配置
  -> 类型 / ID / 引用校验
  -> 稳定排序、字符串池、列表展平、布尔位压缩
  -> GJC2 二进制 + 强类型 C# 代码
  -> 客户端校验并加载列数组
  -> 绑定生成接口、检查客户端必需的字段与引用契约
  -> 后台准备候选快照
  -> 业务边界原子提交
  -> 一次业务操作捕获一个快照
  -> 旧引用释放后回收旧数据
```

编译器、代码生成器和运行时都在包内；Unity Editor 菜单和离线 CLI 复用同一
编译实现，不各写一套格式。包通过标准 UPM 依赖使用 Newtonsoft.Json。

## 3. 框架能力

| 维度 | 已落地的内容 |
| --- | --- |
| 数据表达 | int、long、有限 float、bool、string、int[]，标量与列表跨表引用 |
| 内存 | 列数组、列内字符串共享、列表切片、布尔一位一值，无逐行配置对象 |
| 索引 | 连续 ID 算术定位；高密度带孔 ID 偏移数组；稀疏 ID 可选哈希或二分 |
| 业务 API | 强类型只读行、TryGet/Get、引用导航、结构体遍历、数值只读列 Span |
| 兼容 | 新增字段与列重排兼容；必需字段删除、类型变化、引用改向明确拒绝 |
| 二进制 | 校验长度、校验和、顺序、类型、切片、引用、浮点及布尔填充位 |
| 更新 | Prepare 不发布；Commit 原子替换；拒绝过期、错属、重复及已取消票据 |
| 生命周期 | 旧快照继续有效；取消/提交释放候选引用；无原生指针悬空问题 |
| 验证 | 独立框架测试、游戏回归、真实 Windows IL2CPP、三种规模的强类型对照 |

生成代码不通过反射查字段，也不依赖动态代码生成。GJC1 的动态读取保留兼容，
但包含引用的生成契约不能默许旧格式缺少引用元数据；需要重新编译资源。

## 4. 有技术深度的取舍

### 行视图与批量列读取

业务查一条奖励时用 `Reward.Get(id).Coins`；批量筛选或统计时通过
`Reward.CoinsColumn.TryGetSpan(out var values)` 使用 `ReadOnlySpan<int>`。
Span 的下标是排序后的行位置，不是配置 ID。

这是实测驱动的接口拆分。IL2CPP 下逐行包装的调用开销仍然存在，不能因列存储
就假定所有访问都快。报告保留了较慢的逐行结果，没有拿列扫描偷换原测试。

### 索引速度与内存

同一份二进制支持两种运行时策略。默认快速模式在稀疏表中建立 Dictionary；
紧凑模式使用二分。连续 ID 不再额外分配一个等长索引数组。没有为了制造技术
亮点而手写哈希表。选择由实际 ID 分布和查询频率决定。

### 快照一致性与更新内存

一次战斗、一次奖励结算或一次 UI 重建先 Capture，再从同一个快照读取多张表。
生成行的引用导航回到所属快照，而不是访问全局 Current，避免中途更新后混用版本。

Prepare 在加载前记录基准代次，提交时检查代次，防止慢任务覆盖已经发布的新版本。
读路径是 volatile 引用读取；写端加锁串行提交与取消，不把多发布者问题伪装成
无需同步。原子发布不能让用户自定义的可变对象自动变成线程安全对象。

旧行会持有整个快照，这保证安全，但意味着更新时存在新旧数据共存的内存窗口。
框架没有声称热更新零分配、零峰值或无限保留历史版本。

### 零分配不等于不触发 GC

结论针对预热后的成功读取、引用导航、遍历、列扫描和 Capture。
加载、绑定、提交及异常路径仍会分配。Unity 用经过阳性/空操作校准的 GC.Alloc
事件计数；不会把标记耗时当成字节数，也不会用“没有 GC 回收”证明零分配。

## 5. 最终 IL2CPP 对照

环境：Unity 2022.3.60f1c1，Windows x64，Development，High stripping。
生成接口在独立程序集内，没有为该程序集添加保留全部类型的 linker 配置。
对照是 JsonUtility + 强类型对象数组 + Dictionary，另提供字符串池化版本。

以下为三张表各 10 万行，共 30 万行。托管常驻数值是完整 GC 前后差值估计，
不含已加载输入缓冲，不是进程峰值。加载测 5 轮、查询测 7 轮，交错执行；
计时与分配探测分开。所有实现使用相同逻辑数据和查询序列，检查结果校验和。

| 指标 | 框架快速模式 | 强类型对象基线 | 对象 + 字符串池 | 框架紧凑索引 |
| --- | ---: | ---: | ---: | ---: |
| 常驻托管 MiB | 9.37 | 39.48 | 35.40 | 7.29 |
| 加载与校验 ms | 115.26 | 507.66 | 522.57 | 114.14 |
| 混合读取 ns/次 | 282.62 | 580.43 | 566.17 | 283.74 |
| 稀疏命中 ns/次 | 128.96 | 124.44 | 119.98 | 308.49 |
| 缺失查询 ns/次 | 43.53 | 33.13 | 34.42 | 249.74 |
| 逐行扫描 ns/元素 | 20.51 | 4.80 | 4.37 | 20.32 |
| 批量列扫描 ns/元素 | 0.70 | 4.14 | 2.96 | 0.65 |
| 上述热路径新增托管分配 | 0 | 0 | 0 | 0 |

这一组中，快速模式常驻内存减少约 76%，混合读取约快 2.1 倍，加载约快 4.4 倍。
但小表混合查询可能慢约一倍，稀疏/缺失查询不是普遍更快，逐行扫描也仍然更慢。
这些是设计适用范围，而不是应该隐藏的数字。绝不能据此推断游戏 FPS 提升同等倍数。

另外两个规模是总计 3,000 和 30,000 行；原始 JSON 保留每轮范围及全部工作负载。
输入形状不同也公开记录：源行数组 JSON 约 10.0 MB，对象 JSON 约 18.7 MB，
编译二进制约 7.6 MB。编译成本前移，不代表不存在。

## 6. 验收清单

- 独立 UPM 安装和生成代码编译通过，不引用小游戏代码。
- 30 项框架测试，覆盖标量边界、格式兼容、引用契约、索引、失败隔离和并发。
- 28 项既有游戏消费者回归测试。
- Windows IL2CPP 实际执行 20 万轮读取，空操作 0 事件，阳性 1 事件，读取 0 事件。
- 四种后端、三种规模、五类读取工作负载的结果一致，预热后分配均为零。
- 1000 次更新中被保留的旧快照仍正确；释放后的旧配置图可回收。
- 更新准备期间发生其他提交、并发提交、提交与取消竞争均有测试。
- 保存可复现脚本、原始结果以及包与源码哈希。

这条验收线用于支撑高级客户端面试的高分项目讨论，不把主观面试分数伪装成
自动化测试结果。系统复杂度来自数据契约、更新一致性、生命周期与跨后端性能，
不是把一个配置模块扩张成通用数据库。

## 7. 怎么运行

在 `D:\Packs\GameJsonTown` 下执行：

```powershell
# 直接执行已经构建的 IL2CPP 验证程序，输出性能表
.\scripts\run-framework-benchmark.ps1

# 独立框架测试和原消费者回归
.\scripts\verify-framework.ps1 -IncludeGameRegression

# 从包重新安装、构建并验证，需要本机 Unity / C++ 工具链
.\scripts\verify-framework-unity.ps1 -Target IL2CPP -Benchmark
```

在其他 Unity 2022.3 工程中，从 Package Manager 导入 tgz，再导入 Typed Snapshots
示例即可接入。包内 README 说明编译、生成接口及更新 API。发布包不要求接入小游戏。

## 8. 明确不承诺的部分

没有把 Android/iOS 真机数据、线上生产规模、数小时移动端压力测试或精确更新峰值
算成已完成。没有远程补丁签名、下载器、多文件崩溃恢复、Lua 桥接、任意嵌套 JSON
或整个游戏零 GC 的保证。它们应由实际项目需求驱动，而不是为了凑复杂度加入。
